# Deployment

Two targets. The same application code runs on both.

| | **local** | **aws** |
|---|---|---|
| entry point | `make up` | `make aws-up` |
| defined by | `docker-compose.yml` | `deploy/terraform` + `deploy/k8s` |
| time to stand up | ~3 min | ~25 min |
| cost | nothing | ~USD 0.27/hour, ~195/month |
| teardown | `make down` | `make aws-down` |

Neither is a cut-down version of the other. They make different trades, and
the trades are the interesting part.

---

## What actually differs

Seven services, one broker, one vector index, four logical databases — the
same in both. `services/`, `api/`, `ingest/` and `libs/` are byte-identical
across the two targets. What changes is what the platform hands them.

| | local | aws | why the difference exists |
|---|---|---|---|
| **Postgres** | 4 containers, ephemeral volumes | 1 RDS instance, 4 logical databases | Four RDS instances would be four times the bill for isolation the code already enforces. The boundary that matters is "no service reads another's tables", and that lives in the code, not the instance count. |
| **RabbitMQ** | container, `amqp://` on 5672 | Amazon MQ, `amqps://` on 5671 | Amazon MQ refuses plaintext AMQP. This is the one genuine code difference — `libs/tsevents/src/bus.ts` switches to a TLS socket on the `amqps` scheme. |
| **Topology** | `infra/rabbitmq/definitions.json` imported at boot | declared by the app on connect | Amazon MQ has no definitions import. `assertTopology()` in `libs/tsevents/src/topology.ts` already declares all 7 exchanges, 45 queues and 65 bindings idempotently — so the managed broker gets the same topology, and it survives a broker replacement. The definitions file is a local convenience, not the source of truth. |
| **Secrets** | `fn:fn`, `fn-dev-secret-change-me` in compose | generated by Terraform → Secrets Manager → IRSA → External Secrets → pod env | A hardcoded JWT secret is correct for a laptop and a critical finding anywhere else. No credential in the AWS path is ever in the repo, a manifest, or a shell history. |
| **Scaling** | `docker compose up --scale` | KEDA on RabbitMQ queue depth | A consumer blocked on I/O shows flat CPU, so an HPA scales nothing while the backlog climbs. KEDA reads depth from the broker. `api` still uses a CPU HPA, because that path is genuinely compute-bound. |
| **Ingress** | fixed host ports, nginx | one ALB, path-routed | |
| **Storage** | docker volumes | gp3, `reclaimPolicy: Delete` | `Retain` is the safer production default and the wrong one here: "keeps the volume" means "keeps billing". |
| **Network** | one bridge network, everything reachable | private subnets, security groups, default-deny NetworkPolicies | |

## Local

```bash
make up          # infra, apps, observability
make seed        # ingest + 71 logins + funded accounts
make demo        # reset transactional state for a clean run
```

Ports are in `RUNBOOK.md`. `make down` stops it; `make nuke` removes the data too.

## AWS

### Before the first run

You need a **personal** AWS account — not a work one. `make preflight`
hard-fails on the known Ternary account IDs, because a mistyped profile
putting a portfolio demo into work infrastructure is a mistake worth making
impossible rather than unlikely.

```bash
aws configure --profile fieldnation     # personal account, region ap-southeast-1
cd deploy && make preflight
```

Preflight checks tools, credentials, region reachability, and the two quotas a
new account actually runs out of — 5 Elastic IPs and 5 VPCs per region. Two
failed deploys that left orphans will exhaust the EIP quota, and the resulting
`AddressLimitExceeded` twenty minutes into an apply does not tell you that.

### Standing it up

```bash
make aws-up
```

Which is four phases:

1. **`infra`** — `terraform apply`. VPC, EKS, node group, RDS, Amazon MQ, ECR,
   IRSA roles. ~15 minutes, almost all of it the EKS control plane.
2. **`addons`** — Helm installs the AWS Load Balancer Controller, External
   Secrets, KEDA and metrics-server.
3. **`images`** — builds all seven images `--platform linux/amd64` and pushes
   to ECR. The platform flag is not optional on Apple Silicon; without it the
   push succeeds and the pods crash-loop with `exec format error`, which reads
   like a broken entrypoint rather than a wrong architecture.
4. **`deploy`** — renders the manifests with this account's registry and secret
   ARNs, applies, waits for rollout.

`make aws-status` for pods and nodes, `make -C deploy urls` for the ALB
address.

### Tearing it down

```bash
make aws-down
```

Two steps, and the order is the whole point:

**`pre-destroy.sh` first.** `terraform destroy` on its own fails here, and the
error is unhelpful: it cannot delete the VPC, `DependencyViolation`, no
indication of what depends on it. The cause is that Terraform did not create
the blocker. The ALB behind the Ingress, its ENIs and its security group were
created by a controller inside the cluster in response to a Kubernetes object.
Terraform has never heard of any of them. It deletes the cluster, the ALB
survives, its ENIs stay attached to the subnets, and the VPC will not go.

So the script deletes the Kubernetes objects that own AWS resources —
LoadBalancer Services, Ingresses, PVCs — and then *waits* for AWS to actually
reclaim them, because deleting the Kubernetes object only starts the process.

**`terraform destroy` second**, now that nothing outside its state is holding
the network.

**`verify-destroyed.sh` third**, and this one matters more than it looks.
`terraform destroy` reporting success is not the same as the account being
empty. The script searches **by tag, not by state**, so it finds exactly the
category of thing Terraform never knew about: an orphaned ELB, a log group EKS
created on first write, an EBS volume from a PVC, a snapshot RDS retained
because `skip_final_snapshot` was left off.

If destroy has already failed once and state is half-applied, `make -C deploy
nuke` runs the whole sequence twice, ignoring errors, then reports what
survived.

### The destroyability decisions

Every one of these is the wrong choice for production and the right one here.
They are collected in `deploy/terraform/variables.tf` so the list is
auditable rather than scattered.

| setting | value | what it prevents |
|---|---|---|
| `deletion_protection` | `false` | RDS refusing to be deleted |
| `skip_final_snapshot` | `true` | a retained snapshot billing for storage forever |
| `backup_retention_period` | `0` | automated backups outliving the instance |
| `recovery_window_in_days` | `0` on every secret | the 30-day window reserving the name, so a redeploy fails with "already scheduled for deletion" |
| `force_delete` on ECR | `true` | destroy failing on "repository contains images" |
| `reclaimPolicy: Delete` on gp3 | | EBS volumes surviving their PVCs |
| `log_retention_days` | `3` | log groups retaining forever |
| CloudWatch log groups declared explicitly | | EKS and MQ creating them implicitly, outside state, where destroy cannot reach them |
| local Terraform state | | a remote backend that cannot destroy itself |

That last one is worth expanding. An S3 + DynamoDB backend is the correct
answer for a team, and the wrong answer for a stack whose requirement is that
it disappears completely: the bucket and the lock table are themselves
resources, they must exist before the stack can be created, and
`terraform destroy` cannot remove the state it is currently using. A "fully
destroyable" stack with a remote backend always leaves two resources behind.
The S3 backend block is written and sitting in `backend.tf.disabled`.

## Validating without an AWS account

Everything above can be checked before an account exists:

```bash
make aws-validate
```

`terraform validate` across all four modules, plus `kubeconform` against the
Kubernetes 1.31 schemas for every rendered manifest. No credentials, no
network, no cost.

## Cost

`make aws-cost` prints the current figure. At `sizing=minimal`, roughly
**USD 195/month**, of which:

- **73** EKS control plane — fixed, unavoidable, and the single largest line
- **43** NAT gateway — already reduced from 86 by `single_nat = true`
- **23** two `t3.medium` on SPOT, ~70% off on-demand
- **19** Amazon MQ `mq.t3.micro`
- **18** ALB
- **18** RDS `db.t4g.micro` + 20 GB gp3

The stack bills whether or not it serves a request. A weekend left running is
about USD 13. `sizing=production` is roughly 340/month and exists to show what
the same code looks like when the trades go the other way — on-demand nodes,
NAT per AZ, clustered MQ, multi-AZ RDS.
